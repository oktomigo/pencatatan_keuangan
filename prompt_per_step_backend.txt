## KONTEKS GLOBAL (tempel di awal setiap prompt bila konteks hilang)

```
Proyek: aplikasi pencatatan keuangan harian (PWA), tanpa login, identitas anonim per device.
Stack: Flask (main.py, satu template per route, BUKAN SPA) + MongoDB (pymongo) + Vanilla JS + Tailwind CDN.
Dokumen acuan: requirements.md (Requirement 1–10), design.md (tokens, komponen, error messages), rencana_kerja.txt.
Fase 1–2 sudah selesai: semua template Jinja2 + static/js/*.js sudah ada dan jalan dengan data MOCK.
Aturan arsitektur:
- static/js/ hanya berisi behavior/DOM update — TIDAK generate halaman HTML baru.
- Template HTML TIDAK boleh berubah di Fase 3–4 kecuali diminta eksplisit.
- Semua data milik satu device diisolasi lewat field device_id.
- Uang disimpan sebagai integer rupiah (tanpa desimal), maksimum 999999999999.
- Tanggal disimpan sebagai string ISO 8601 "YYYY-MM-DD".
- Pesan error WAJIB persis sama dengan tabel "Error Messages (Standard)" di design.md.
```

### Konvensi Response API (dipakai semua step)

```
Sukses : 200/201 { "success": true, "data": <objek|array>, "meta": {...opsional} }
Gagal  : 4xx/5xx { "success": false, "error": { "code": "VALIDATION_ERROR",
                                                "message": "<pesan user-facing>",
                                                "fields": { "amount": "Nominal wajib diisi" } } }
Kode error: VALIDATION_ERROR (400), DEVICE_REQUIRED (401), NOT_FOUND (404),
            CONFLICT (409), STORAGE_ERROR (500)
Semua endpoint /api/* wajib header X-Device-ID, kecuali POST /api/init.
```

### Skema MongoDB (acuan tetap untuk semua step)

```
devices          { _id, device_id, created_at, last_seen_at, seeded }
categories       { _id, device_id, name, type('income'|'expense'), is_default, icon, color, created_at }
transactions     { _id, device_id, type, amount(int), date('YYYY-MM-DD'), category_id, note, created_at, updated_at }
budgets          { _id, device_id, category_id, amount(int), period('monthly'|'weekly'), created_at, updated_at,
                   notified_80(bool), notified_100(bool), notified_period(str) }
recurring_bills  { _id, device_id, name, amount(int), due_day(int), frequency('monthly'|'weekly'|'yearly'),
                   next_due('YYYY-MM-DD'), is_active(bool), category_id, last_paid_at, created_at }
savings_goals    { _id, device_id, name, target_amount(int), saved_amount(int), deadline('YYYY-MM-DD'),
                   status('active'|'completed'|'overdue'), created_at, completed_at }
savings_entries  { _id, device_id, goal_id, amount(int), date, note, created_at }

Index wajib:
  categories      : (device_id, type), unique (device_id, type, name_lower)
  transactions    : (device_id, date desc), (device_id, category_id)
  budgets         : unique (device_id, category_id, period)
  recurring_bills : (device_id, next_due)
  savings_goals   : (device_id, status)
```

## STEP 3.1 — Setup Backend

**PROMPT**

```
Kerjakan STEP 3.1 — Setup Backend. HANYA step ini, jangan menyentuh logika bisnis.

Buat/ubah file:
1. requirements.txt  → flask, pymongo, flask-cors, openpyxl, fpdf2, python-dotenv
   (pin versi minor, contoh flask==3.0.*; jangan pakai versi yang baru rilis <7 hari).
2. config.py → class Config membaca env via python-dotenv:
   MONGO_URI (default mongodb://localhost:27017), MONGO_DB (default pencatatan_keuangan),
   FLASK_ENV, SECRET_KEY, CORS_ORIGINS, MAX_AMOUNT=999999999999.

4. db.py → modul koneksi MongoClient singleton:
   - get_db() mengembalikan objek Database
   - init_indexes() membuat SEMUA index sesuai skema di konteks global (idempoten)
   - dipanggil sekali saat app start
5. main.py → daftarkan CORS, load Config, panggil init_indexes() saat startup,
   tambahkan GET /api/health yang mengembalikan {"success": true, "data": {"db": "ok"}}

   sesuai konvensi response di konteks global.
7. .gitignore: pastikan .env, __pycache__, *.pyc, venv/ diabaikan.

Verifikasi sebelum selesai:
- `pip install -r requirements.txt` berhasil.
- Flask start tanpa error, `curl localhost:5000/api/health` → {"success": true, ...}.
- Semua route halaman Fase 1–2 masih bisa dibuka normal.

Jangan implementasikan CRUD apa pun di step ini.
```

**PROMPT**

```

3. Tulis test manual singkat di scripts/smoke_3_2.sh (curl) yang membuktikan idempotensi.

Verifikasi:
- POST /api/init tanpa body → dapat device_id baru + 11 kategori default.
- POST /api/init 3x dengan device_id sama → jumlah kategori tetap 11.
- GET /api/transactions tanpa header X-Device-ID → 401 DEVICE_REQUIRED.

Belum menyentuh frontend sama sekali.

## STEP 3.3 — Backend Kategori

**PROMPT**

```
Kerjakan STEP 3.3 — Backend Kategori. Acuan: requirements.md Requirement 2 (2.1–2.7),
design.md Property 5 & 6, dan error message standar.

Endpoint (semua ber-scope device_id dari flask.g):
  GET    /api/categories?type=income|expense   → list kategori, default dulu lalu custom, sort by name
  POST   /api/categories                        → { name, type, icon?, color? }
  PUT    /api/categories/<id>                   → { name?, icon?, color? }
  DELETE /api/categories/<id>?reassign_to=<id>  → hapus, opsional pindahkan transaksi

Aturan wajib:
1. name: wajib, trim, maks 50 char. Kosong → "Nama kategori wajib diisi".
2. Unik case-insensitive dalam (device_id, type). Simpan field turunan name_lower untuk unique index.
   Duplikat → 409 CONFLICT dengan message PERSIS "Nama kategori sudah digunakan".
3. Batas maks 50 kategori custom per tipe → 400 "Maksimal 50 kategori per tipe".
4. Kategori is_default=true: PUT dan DELETE ditolak 400 "Kategori default tidak dapat diubah".
5. Rename: karena transaksi menyimpan category_id (bukan nama), rename otomatis terpropagasi.
   Tulis test yang membuktikan semua transaksi terkait mengembalikan nama baru saat di-join (Property 6).
6. DELETE:
   - Jika kategori tidak punya transaksi → hapus langsung, hapus juga budget yang terkait.
   - Jika punya transaksi dan reassign_to TIDAK diberikan → 409 dengan
     { code: "CONFLICT", message: "Kategori masih memiliki transaksi",
       data: { transaction_count: N, available_targets: [ {id, name} ] } }
   - Jika reassign_to diberikan → validasi target ada, bertipe sama, bukan dirinya sendiri;
     pindahkan semua transaksi (update_many) lalu hapus kategori.
   - Jika tidak ada kategori lain bertipe sama → available_targets: [] (frontend akan menonaktifkan opsi pindah).
7. Semua response mengembalikan id sebagai string (str(ObjectId)), bukan ObjectId mentah.

Verifikasi (tulis tests/test_categories.py, pytest):
- Buat "Makanan" lalu "makanan" → 409 dengan pesan persis.
- Hapus kategori bertransaksi tanpa reassign → 409 + transaction_count benar.
- Hapus dengan reassign → transaksi pindah, jumlah transaksi total tidak berubah.
- Kategori default tidak bisa dihapus/diedit.

Frontend belum disentuh.
```

## STEP 3.4 — Backend Transaksi

**PROMPT**

```
Kerjakan STEP 3.4 — Backend Transaksi. Acuan: requirements.md Requirement 1 (1.1–1.10),
design.md Property 1–4 dan error messages.

Endpoint:
  GET    /api/transactions?month=&year=&type=&category_id=&q=&start=&end=&limit=&skip=
  POST   /api/transactions
  GET    /api/transactions/<id>
  PUT    /api/transactions/<id>
  DELETE /api/transactions/<id>

Validasi POST/PUT (kembalikan SEMUA field error sekaligus di error.fields):
- type      : wajib, harus 'income' | 'expense'      → "Jenis wajib dipilih"
- amount    : wajib, integer > 0 dan <= 999999999999 → kosong: "Nominal wajib diisi";
              invalid: "Nominal harus berupa angka lebih dari 0 dan tidak melebihi 999.999.999.999"
              Tolak string non-numerik, NaN, float non-integer, dan nilai negatif.
              Simpan sebagai int (BUKAN float) agar presisi tidak hilang.
- date      : wajib, format YYYY-MM-DD valid        → "Tanggal wajib diisi" / "Tanggal tidak valid"
- category_id: wajib, ada di device ini, dan type kategori HARUS sama dengan type transaksi
              → "Kategori wajib dipilih" / "Kategori tidak valid"
- note      : opsional, maks 255 char               → "Catatan maksimal 255 karakter"

Aturan lain:
1. created_at & updated_at ISO 8601 UTC; PUT hanya mengubah updated_at.
2. GET list: default sort date desc lalu created_at desc (transaksi baru selalu paling atas).
3. Filter: month+year, atau start+end (rentang inklusif). Jika start > end → 400
   "Tanggal mulai tidak boleh setelah tanggal akhir". Parameter q = pencarian di note (case-insensitive).
4. Setiap item list disertai category_name, category_icon, category_color (lookup/aggregate $lookup),
   supaya frontend tidak perlu request kedua.
5. meta: { total, limit, skip, total_income, total_expense, balance } untuk filter yang sedang aktif.
6. DELETE: hard delete, response 200 { success: true, data: { id } }. 404 jika id bukan milik device ini.
7. Jangan pernah membocorkan data device lain — semua query WAJIB menyertakan device_id.

Verifikasi (tests/test_transactions.py):
- Round-trip: POST lalu GET by id menghasilkan nilai identik (Property 1).
- amount = 0, -1, 1e12, "abc", 12.5 → semua ditolak dengan pesan persis (Property 2).
- Body kosong → error.fields memuat keempat field wajib (Property 3).
- PUT mengubah nilai → GET mengembalikan nilai baru, bukan lama (Property 4).
- Filter month/year hanya mengembalikan transaksi di bulan tsb.
```

## STEP 3.6 — Backend Anggaran

**PROMPT**

```
Kerjakan STEP 3.6 — Backend Anggaran. Acuan: requirements.md Requirement 3 (3.1–3.9),
design.md Budget Calculation Logic + Property 7 & 8.

Endpoint:
  GET    /api/budgets?period=monthly|weekly   → semua budget + perhitungan realtime
  POST   /api/budgets                          → { category_id, amount, period }
  PUT    /api/budgets/<id>                     → { amount?, period? }
  DELETE /api/budgets/<id>

Aturan:
1. amount: integer > 0 dan <= 999999999999; invalid → 400 message PERSIS "Nominal anggaran tidak valid".
2. category_id wajib ada, milik device ini, dan HARUS bertipe 'expense' → "Kategori tidak valid".
3. Satu kategori hanya boleh punya satu budget per period → 409 "Anggaran kategori ini sudah ada"
   (frontend akan mengarahkan ke edit).
4. Setiap item GET memuat: amount, spent, remaining, percentage, status, dan category info.
   percentage = (spent / amount) * 100 dibulatkan 1 desimal; gunakan pembagian presisi cukup
   agar threshold 80% dan 100% tidak salah klasifikasi.
5. Status: "safe" (<80), "warning" (80–99.99), "danger" (>=100).
6. Notifikasi one-time per periode: simpan notified_80, notified_100, notified_period ("2026-09" atau "2026-W38").
   Jika periode berjalan berbeda dengan notified_period → reset kedua flag.
   Response menyertakan "notify": "warning" | "danger" | null HANYA pada kali pertama threshold tercapai,
   lalu set flag-nya. Pesan danger PERSIS: "Anggaran [Nama Kategori] telah terlampaui".
7. PUT amount → hitung ulang status dari transaksi yang SUDAH ada di periode yang sama (Requirement 3.8),
   dan evaluasi ulang flag notifikasi.
8. Kategori tanpa budget tidak muncul di endpoint ini (frontend menampilkan tanpa indikator).
9. Pencatatan transaksi TIDAK PERNAH diblokir walau budget terlampaui — pastikan tidak ada guard di step 3.4.

Verifikasi (tests/test_budgets.py):
- spent/amount = 0.79 → safe; 0.80 → warning; 1.00 → danger (boundary tepat).
- notify hanya muncul sekali per periode per threshold.
- Ubah amount sehingga persentase turun di bawah 80 → status kembali safe.
```

- Untuk kumpulan transaksi acak, total_income/total_expense/balance cocok dengan hitungan manual.
- daily_trend punya jumlah elemen == jumlah hari dalam periode.

## STEP 3.8 — Backend Tagihan Berulang

**PROMPT**

```
Kerjakan STEP 3.8 — Backend Tagihan Berulang. Acuan: requirements.md Requirement 5 (5.1–5.7), Property 11.

Endpoint:
  GET    /api/recurring-bills?status=upcoming|all
  POST   /api/recurring-bills          → { name, amount, due_day, frequency, category_id?, start_date? }
  PUT    /api/recurring-bills/<id>
  DELETE /api/recurring-bills/<id>
  POST   /api/recurring-bills/<id>/pay → tandai lunas periode berjalan

Aturan:
1. Validasi: name wajib maks 50 char; amount integer > 0 <= 999999999999
   (pesan nominal PERSIS seperti standar); frequency 'monthly'|'weekly'|'yearly';
   due_day 1–31 untuk monthly, 0–6 untuk weekly, untuk yearly gunakan due_date (MM-DD).
2. Hitung next_due saat create dan setiap kali dibayar:
   - monthly : tanggal due_day pada bulan berikutnya; jika due_day > jumlah hari bulan tsb,
               pakai hari terakhir bulan itu (31 → 28/29 Februari).
   - weekly  : hari due_day berikutnya (0=Senin).
   - yearly  : tanggal yang sama tahun berikutnya (29 Feb → 28 Feb pada tahun non-kabisat).
   Tulis fungsi murni calc_next_due(current_date, frequency, due_day) di helper terpisah + unit test.
3. POST /pay:
   - Buat transaksi expense otomatis: amount, name bill masuk ke note (atau nama),
     date = tanggal jatuh tempo periode berjalan, category_id dari bill
     (fallback kategori "Tagihan" milik device).
   - Set last_paid_at, majukan next_due sesuai frekuensi.
   - Response berisi { bill: <bill terbaru>, transaction: <transaksi yang dibuat> }.
   - Idempoten dalam satu periode: memanggil /pay dua kali untuk periode yang sama → 409
     "Tagihan ini sudah ditandai lunas untuk periode ini" (jangan buat transaksi dobel).
4. GET status=upcoming → hanya bill aktif dengan next_due <= hari ini + 7 hari,
   disertai days_left dan is_due_today.
5. DELETE bill: hapus bill saja. Transaksi yang sudah tercatat TIDAK ikut terhapus (Requirement 5.7).
6. Endpoint mengembalikan data yang cukup bagi frontend untuk membuat in-app notification
   (tidak ada scheduler server; penjadwalan notifikasi dilakukan di klien).

Verifikasi (tests/test_recurring_bills.py):
- /pay membuat tepat satu transaksi expense dengan nominal identik (Property 11).
- next_due maju sesuai frekuensi; kasus due_day=31 di bulan Februari benar.
- /pay kedua di periode sama → 409 dan jumlah transaksi tidak bertambah.
```

## STEP 3.9 — Backend Target Tabungan

**PROMPT**

```
Kerjakan STEP 3.9 — Backend Target Tabungan. Acuan: requirements.md Requirement 6 (6.1–6.7),
design.md Savings Estimation Logic + Property 12.

Endpoint:
  GET    /api/savings-goals?status=active|completed|overdue|all
  POST   /api/savings-goals            → { name, target_amount, deadline }
  PUT    /api/savings-goals/<id>
  DELETE /api/savings-goals/<id>
  POST   /api/savings-goals/<id>/add-funds → { amount, date?, note? }
  GET    /api/savings-goals/<id>/entries

Aturan:
1. Validasi: name wajib maks 50 char; target_amount integer > 0 <= 999999999999
   (pesan nominal standar); deadline format YYYY-MM-DD dan tidak boleh di masa lalu saat create
   → "Tanggal target tidak boleh di masa lalu".
2. saved_amount awal 0, progress 0%. add-funds menambah saved_amount dan mencatat savings_entries.
   amount add-funds harus > 0. Boleh melebihi target (progress ditampilkan 100%).
3. percentage = (saved_amount / target_amount) * 100, 1 desimal, di-cap 100 untuk tampilan
   tetapi kirim juga raw_percentage.
4. Status dihitung ulang setiap kali data dibaca/diubah:
   - completed : saved_amount >= target_amount (set completed_at sekali saja)
   - overdue   : deadline < hari ini DAN saved_amount < target_amount
   - active    : selain itu
5. Estimasi: kirim months_remaining, amount_needed, required_monthly, avg_monthly_saving,
   dan on_track (bool) sesuai rumus di design.md. Jika months_remaining <= 0, required_monthly = null.
6. Saat transisi pertama kali ke completed, response menyertakan
   "notify": "Selamat! Target [Nama Target] telah tercapai!" (sekali saja, pakai completed_at sebagai penanda).
7. DELETE goal: hapus goal + savings_entries-nya; transaksi keuangan tidak terpengaruh.

Verifikasi (tests/test_savings.py):
- add-funds berkali-kali → saved_amount = jumlah semua entry.
- percentage & status sesuai aturan untuk kombinasi (saved, target, deadline) (Property 12).
- notify hanya muncul sekali.
```

   - generate_pdf(data) dengan fpdf2:
     Header judul + periode, blok ringkasan, lalu tabel transaksi terurut tanggal,
     page break otomatis + header tabel berulang + nomor halaman. Nominal diformat Rp dengan pemisah ribuan.
     Gunakan font yang mendukung karakter Indonesia (tanpa karakter non-latin1 yang bikin error).
2. Nama file: keuangan_<YYYYMMDD>_<YYYYMMDD>.xlsx / .pdf
3. Jika tidak ada transaksi pada periode → 400
   { code: "VALIDATION_ERROR", message: "Tidak ada data transaksi pada periode ini" } dan TIDAK menghasilkan file.
4. Bila generasi gagal → 500 message PERSIS "Ekspor gagal, silakan coba lagi";
   pastikan tidak ada file parsial tertinggal (bangun di BytesIO, kirim via send_file, jangan tulis ke disk).
5. Batas aman: maksimum 50.000 transaksi per ekspor; lebih dari itu → 400 "Data terlalu besar, persempit periode".

Verifikasi (tests/test_export.py):
- File Excel berisi TEPAT semua transaksi dalam periode, tidak ada dari luar periode (Property 13);
  baca ulang file hasil dengan openpyxl untuk menghitung baris.
- PDF terbentuk, ukuran > 0, dan jumlah transaksi pada data sumber sama dengan yang di-render.
- Periode kosong → 400 dengan pesan persis.
```

## STEP 4.1 — api.js (Fetch Wrapper)

**PROMPT**

```
Kerjakan STEP 4.1 — static/js/api.js. Ini fondasi semua step Fase 4 berikutnya.

Implementasikan dan export:
1. getDeviceId() — ambil 'device_id' dari localStorage; jika belum ada, POST /api/init
   (tanpa body) lalu simpan device_id dari response. Pastikan hanya SATU panggilan /api/init
   walau beberapa modul memanggil bersamaan (cache promise-nya).
2. apiFetch(path, options) —
   - Otomatis menambah header X-Device-ID dan Content-Type: application/json.
   - options: { method, body (objek, otomatis JSON.stringify), query (objek → querystring), signal }.
   - Parse response: jika success true → return data (dan simpan meta di properti hasil bila ada).
   - Jika success false → throw ApiError { code, message, fields, status }.
   - Jika HTTP 401 DEVICE_REQUIRED → panggil /api/init sekali lalu retry request satu kali.
   - Timeout 15 detik via AbortController → ApiError code "TIMEOUT",
     message "Gagal memuat data. Coba refresh halaman."
   - Offline (navigator.onLine === false) → langsung throw ApiError code "OFFLINE" tanpa request.
3. apiDownload(path, body, filename) — POST yang menerima blob, buat object URL, trigger <a download>,
   lalu revokeObjectURL (hindari file parsial / memory leak).
4. Helper UI (dipakai step berikutnya): withLoading(el, fn) yang menampilkan .skeleton saat loading
   dan menampilkan blok error + tombol "Coba lagi" saat gagal.
5. Semua error yang tidak punya pesan user-facing ditampilkan sebagai
   "Gagal memuat data. Coba refresh halaman." lewat showToast(..., 'error').

Verifikasi:
- Buka halaman mana pun → localStorage terisi device_id, Network tab menunjukkan /api/init hanya sekali.
- Matikan jaringan (DevTools offline) → muncul toast/banner offline, bukan exception mentah.

Belum mengubah halaman mana pun di step ini.
```
